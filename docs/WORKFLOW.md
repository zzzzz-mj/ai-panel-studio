# 开发过程思路 & 工作流说明

> Prompt 原文见 [PROMPTS.md](./PROMPTS.md)（P1–P8），下文沿用同一套编号。

## 1. 开发工作流：TraeCode + DeepSeek V4.1 Flash

工具是 **TraeCode**（TRAE 的 AI 原生 IDE），接入模型 **DeepSeek V4.1 Flash**。

> 题面以「Claude Code + DeepSeek V4 Pro」举例，本项目的实际工具链是 TraeCode + DeepSeek V4.1 Flash。两者同属「AI 原生 IDE / Coding Agent + 大模型」这一形态，下文的分层交付流程与三个典型问题都出自真实开发过程。

这个项目没有用「一句话生成」。我把它拆成八次对话，每次都只要一层东西，跑通了才进下一轮。

第一轮（P1，SDD）只要文档，我还在 Prompt 里写了一句「不要生成代码」。模型一旦同时输出文档和实现，就会拿实现细节去凑文档，契约里本该划清楚的边界反而被绕过去。这一轮出来的是 PRD / ER / API 三份，之后它们成了每一轮的验收基准。写数据层、引擎层、前端时我都不用再复述产品，说一句「按 `docs/API.md` 实现」就够。

往后每一层我都留了个能跑起来的验证点。数据层（P2）看 `npm run db:reset` 能不能打出「预置议题 6 条，样例讨论 3 场」；核心逻辑（P5，TDD）看先写的测试能不能绿；接口层（P6，E2E）看「建讨论 → 生成阵容 → 开播 → 拉 transcript → 校验总结」这一整条跑不跑得通。这是我这次体会最深的：AI 写代码很快，真正花时间的是怎么确认它写对了。验证点提前定好，比反复调 Prompt 管用得多。

范式是分阶段用的，不是往文档上贴标签。SDD 只管数据建模和契约（P1、P2）；DDD 用在前端，先出 `.uicraft.md`（深色单主题、琥珀金主持人色、8 色嘉宾身份色板，最后固化进 `tokens.css`），再生成三页界面和实时流（P3、P4）；TDD 管核心逻辑（P5）；E2E 收口（P6）。同一个需求换一种约束方式去问，模型输出的稳定性差别很明显。

## 2. 三个典型问题

**问题一：AI 默认写成「两步写入」，把 SSE 断线续传的前提破坏了。** `transcript_entry` 和 `discussion_event` 必须共用一个单调递增的 `seq`，它既是 transcript 的排序键，也是 SSE 的 `Last-Event-ID` 游标。AI 第一版是先插 transcript 再插 event，可两次自增主键不保证相等，一旦并发或回滚，游标就错位，前端重连要么丢发言要么重复发言。我把这条不变量写成数据层的硬性要求，`repo.appendTranscript` 在一个事务里显式生成一次 `seq` 给两张表共用，前端再按 `id` 幂等 upsert、按 `seq` 排序兜一层。跨表一致性、断线续传这类不变量必须在 Prompt 里点明并说清怎么验收，模型的默认写法几乎总是「能跑，但不安全」的那一版。

**问题二：7 个测试红了，得先分清是测试写错还是实现有 bug。** 最省事的做法是把断言放宽让它们全绿，但那等于把真实缺陷埋掉。我逐条归位：`clampSentences` 遇到没有标点的长句时先截断再拼省略号，总长超出上限 1 个字符，这是实现的问题，改成 `slice(0, max - 1) + '…'`，让上限变成硬上限；E2E 里「每次发言 1-2 句」失败，查下来是主持人收尾总结按设计就是整段自然语言，那是测试的问题，改测试（`if (entry.intent === 'summary') continue`）。我给自己定的规矩是：红了的用例，先回答「错在哪一侧」才能动手改。最后 62 项全绿，是实现和断言都站得住的绿。

**问题三：Prompt 只能引导，硬约束得靠代码兜底。** 「每次发言 1-2 句」写进了系统提示词，但温度调到 0.9 追求观点发散之后，真实模型还是会吐三四句，甚至带出 `"intent": "rebuttal"` 这种 JSON 片段。所以我在 LLM 层加了确定性的后处理：`cleanUtterance` 剥掉 markdown 和 JSON 残留，`clampSentences` 按句数和字数硬裁，`parseJsonLoose` 三级降级（代码围栏 → 首尾大括号 → 容错解析），解析失败返回兜底值，不让整场讨论崩掉。引导模型往对的方向走是 Prompt 的事，保证它走不到错的地方是代码的事，真正算工程化的是后面这一半。

## 3. 我对「工程化 AI 开发」的理解

最大的变化是：写代码变便宜了，「说清楚什么是对的」反而成了主要工作量。

AI 很擅长填空，不擅长划边界。你说「实现一个圆桌讨论引擎」，它能给你一版能跑的东西；但「每次发言 1-2 句」「禁止机械式轮流发言」「共识要实时增量，不能等结束再生成」「多场讨论必须隔离」这些，它不会主动想。划边界是人的活，而且得写成能验收的形式（测试、断言、验收点），不然就只是一句愿望。

分层交付也比一次生成可控。一次生成整个项目，出问题面对的是一个巨大的黑盒；分成契约 → 数据 → 设计 → 界面 → 引擎 → 接口之后，每层都有自己的验证点，出错能定位到具体某一层。模型在「上下文小、验收口径明确」的时候，输出质量也明显更高。

还有一点，工程化的痕迹应该留在仓库里，不是留在对话里。契约文档、测试用例、分层的提交历史、Prompt 记录，这些不只是给评审看的，它们本身就是下一轮对话的输入。把 `docs/API.md` 当契约、把测试当验收口径，本质上是把已经想清楚的部分固化下来，让 AI 每轮不用重新猜。这次 62 项测试全绿、前端 `tsc --noEmit` 和 `vite build` 都过、本地零配置能跑通完整流程，靠的是「先定契约 → 分层实现 → 每层验收」这套东西，不是某一次特别成功的 Prompt。
