# 开发过程思路 & 工作流说明

> Prompt 原文见 [PROMPTS.md](./PROMPTS.md)（P1–P8），下文沿用同一套编号。

## 1. 开发工作流：Claude Code + DeepSeek V4 Pro

工具是 **Claude Code**，接入模型 **DeepSeek V4 Pro**。项目没有「一句话生成」，而是拆成八次可验收的对话，每次只让 AI 交付**一层**，验收通过才进下一层。

**先定契约，再写代码。** 第一步（P1，SDD）只要文档，并明确写了「不要生成代码」—— 一旦让模型同时输出文档和实现，它就会用实现细节去迁就文档，契约里该有的边界反而被跳过。产出的 `PRD` / `ER` / `API` 成了后续所有对话的验收基准：写数据层、引擎层、前端时不必复述产品，只说「按 `docs/API.md` 实现」。

**每一层都带一个可运行的验证点。** 数据层（P2）验证 `npm run db:reset` 能打出「预置议题 6 条，样例讨论 3 场」；核心逻辑（P5，TDD）验证先写的测试能否跑绿；接口层（P6，E2E）验证「建讨论 → 生成阵容 → 开播 → 拉 transcript → 校验总结」整条链路。**AI 写代码很快，真正的成本不在产出，而在「怎么知道它写对了」** —— 把验证点前置是这次最大的效率来源。

**范式分阶段，不是贴标签。** SDD 用于数据建模与契约（P1、P2）；DDD 用于前端，先产出 `.uicraft.md`（深色单主题、琥珀金主持人色、8 色嘉宾身份色板，固化进 `tokens.css`）再生成三页界面与实时流（P3、P4）；TDD 用于核心逻辑（P5）；E2E 用于质量闭环（P6）。同一需求换一种约束方式提问，模型输出的稳定性差异非常明显。

## 2. 三个典型问题与解决路径

**问题一：AI 默认写「两步写入」，破坏 SSE 断线续传的前提。** `transcript_entry` 与 `discussion_event` 必须共享同一个单调递增的 `seq`，它既是 transcript 的排序键，也是 SSE 的 `Last-Event-ID` 游标。AI 第一版是「先插 transcript 再插 event」，但两次自增主键**不保证相等**，并发或回滚时游标错位，前端重连就会丢发言或重复发言。**解决**：把这条不变量写成数据层硬性要求，`repo.appendTranscript` 在一个事务里显式生成一次 `seq` 供两表共用；前端再按 `id` 幂等 upsert + `seq` 排序兜一层。**教训：跨表一致性、断线续传这类不变量必须在 Prompt 里点明并给出验收方式 —— 模型的默认写法几乎总是「能跑但不安全」的那版。**

**问题二：7 个测试失败，先分类「测试写错」还是「实现有 bug」。** 最省事的做法是放宽断言让它们全绿，但那等于埋掉真实缺陷。逐条归位：`clampSentences` 处理无标点长句时先截断再拼省略号，总长超出上限 1 个字符 —— 实现问题，改实现（`slice(0, max - 1) + '…'`），让上限成为**硬上限**；E2E 里「每次发言 1-2 句」失败，排查发现主持人收尾总结按设计就是整段自然语言 —— 测试问题，改测试（`if (entry.intent === 'summary') continue`）。**解决**：定规矩 —— 红了的用例必须先回答「错在哪一侧」才能动手。最终 62 项全绿，是实现和断言都站得住的绿。

**问题三：Prompt 只能引导，硬约束必须靠代码兜底。** 「每次发言 1-2 句」写进了系统提示词，但温度 0.9 追求观点发散时，真实模型仍会输出三四句，甚至带出 `"intent": "rebuttal"` 这类 JSON 片段。**解决**：在 LLM 层加确定性后处理 —— `cleanUtterance` 剥离 markdown / JSON 残留，`clampSentences` 按句数与字数硬裁剪，`parseJsonLoose` 三级降级（代码围栏 → 首尾大括号 → 容错解析），解析失败返回兜底值而不是让整场讨论崩掉。**Prompt 负责引导模型往对的方向走，代码负责保证它走不到错的地方 —— 后者才是工程化的部分。**

## 3. 我对「工程化 AI 开发」的理解

一句话：**AI 让「写代码」变便宜了，于是「定义什么是对的」成了主要工作量。**

**一、AI 擅长填空，不擅长划边界。** 说「实现一个圆桌讨论引擎」，它能给一版能跑的实现；但「每次发言 1-2 句」「禁止机械式轮流发言」「共识要实时增量而非结束时生成」「多场讨论必须隔离」这些边界它不会主动想。**划边界是人的工作**，且必须写成可验收的形式（测试、断言、验收点），否则只是一句愿望。

**二、分层交付比一次生成更可控。** 一次生成整个项目，出问题时面对一个巨大黑盒；分层交付（契约 → 数据 → 设计 → 界面 → 引擎 → 接口）每层都有独立验证点，出错能精确定位到某一层，模型在「小上下文 + 明确验收口径」下的输出质量也更高。

**三、工程化痕迹应留在仓库里，而不是对话里。** 契约文档、测试用例、分层提交历史、Prompt 记录的价值不只是给评审看 —— 它们是**下一次对话的输入**。把 `docs/API.md` 当契约、把测试当验收口径，本质是把「已想清楚的部分」固化成 AI 可反复读取的上下文，避免它每轮重新猜。这次 62 项测试全绿、前端 `tsc --noEmit` 与 `vite build` 双双通过、本地零配置可跑通完整流程，靠的不是某一次特别成功的 Prompt，而是「先定契约 → 分层实现 → 每层验收」这套流程本身。
