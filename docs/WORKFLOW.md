# 开发过程思路 & 工作流说明

## 1. 我的开发工作流：Claude Code + DeepSeek V4 Pro

这次作业我用的 Vibe Coding 工具是 **Claude Code**，接入的模型是 **DeepSeek V4 Pro**。整个项目没有「一句话生成」，而是把它拆成七次可验收的对话，每一次只让 AI 交付**一层**，验收通过才进入下一层。这条主线的依据是 [PROMPTS.md](./PROMPTS.md) 里的 P1–P7。

**先定契约，再写代码。** 第一步（P1，SDD 范式）我只要文档，明确写了一句「不要生成代码」：一旦让模型同时输出文档和实现，它就会用实现细节去迁就文档，契约里该有的边界情况反而被跳过。产出的 `docs/PRD.md` / `ER.md` / `API.md` 成了后面所有对话的「验收基准」——写数据层、引擎层、前端时我不需要再复述一遍产品，只需要说「按 `docs/API.md` 实现」。这一步还顺手逼出了「不做清单」，把通知、权限、多用户这些 MVP 之外的东西挡在门外。

**每一层都带一个可运行的验证点。** 数据层（P2）的验证点是 `npm run db:reset` 能打出「预置议题 6 条，样例讨论 3 场」；引擎层（P4，TDD 范式）的验证点是先写测试再写实现，跑不绿就不进入下一层；接口层（P5，E2E 范式）的验证点是一条完整的「建讨论 → 生成阵容 → 开播 → 拉 transcript → 校验总结」端到端链路。**AI 写代码很快，所以真正的成本不在产出，而在「怎么知道它写对了」**——把验证点前置，是我这次最大的效率来源。

**范式是分阶段的，不是贴标签。** SDD 用在数据建模与 API 契约（P1、P2 前半），DDD 用在设计上下文与前端组件拆解（P3：先让 AI 输出 `.uicraft.md` 设计方向与组件清单，再逐个组件实现），TDD 用在核心逻辑（P4：发言排序、JSON 容错裁剪），E2E 用在系统级质量闭环（P5）。同一个需求在不同阶段用不同的约束方式提问，模型输出的稳定性差异非常明显。

**前端我刻意「先设计后编码」。** P3 先产出 `.uicraft.md`：深色演播厅单主题、舞台琥珀金 `#E7B24A` 作主持人色、8 色嘉宾身份色板、衬线标题配无衬线正文。有了这份「设计令牌」再写 CSS，组件之间才不会各写各的颜色和间距——颜色在这个产品里是身份标识，必须全局唯一。

## 2. 三个典型问题与解决路径

### 问题一：AI 默认写「两步写入」，破坏了 SSE 断线续传的前提

`transcript_entry` 和 `discussion_event` 需要共享同一个单调递增的 `seq`，它同时是 transcript 的排序键和 SSE 的 `Last-Event-ID` 续传游标。AI 的第一版实现是「先 `INSERT INTO transcript_entry`，再 `INSERT INTO discussion_event`」——看起来很自然，但两次自增主键**不保证相等**，一旦有并发写入或事务回滚，游标就会错位，前端重连后会丢发言或重复发言。

**解决路径**：把这条约束提升为「数据层的硬性要求」写进 Prompt，而不是指望它自己想到。最终 `repo.appendTranscript` 在一个事务里显式生成一次 `seq`，两张表共用同一个值。配套的前端策略是 `id` 幂等 upsert + `seq` 排序：即使 EventSource 自动重连导致重复投递，也不会产生重复内容。**教训是：涉及「跨表一致性 / 断线续传」这类不变量，必须在 Prompt 里点明并给出验收方式，模型的默认写法几乎总是「能跑但不安全」的那一版。**

### 问题二：7 个测试失败，要先分类「测试写错」还是「实现有 bug」

跑完第一轮测试有 7 条红的。最省事的做法是把断言改宽松让它们全绿，但那样等于把真实缺陷埋掉。我逐条归位，分成两类：

- **实现有 bug**：`clampSentences` 处理「无标点长句」时，按上限截断后再拼省略号，总长度会超出上限 1 个字符。这是实现问题，改实现——`slice(0, max - 1) + '…'`，让 `maxCharsPerSentence` 成为真正的**硬上限**，而不是事后在测试里放宽断言。
- **测试写错**：E2E 里「每次发言 1-2 句」得 10 句，排查发现主持人收尾总结按设计就是整段自然语言，本就不该受这条约束。这是测试问题，改测试——断言里 `if (entry.intent === 'summary') continue;`。

**解决路径**：定了一条规矩——**红了的用例必须先回答「它错在哪一侧」，才能动手改**。最后 62 项全绿，而且是「实现和断言都站得住」的绿。

### 问题三：Prompt 只能引导，硬约束必须靠代码兜底

需求里「每次发言控制在 1-2 句」我写进了系统提示词，但真实模型（尤其温度调到 0.9 追求观点发散时）仍会偶尔输出三四句，甚至带出 `"intent": "rebuttal"` 这类 JSON 片段。**光靠 Prompt 约束是不可靠的。**

**解决路径**：在 LLM 层加一道确定性后处理——`cleanUtterance` 剥离 markdown / JSON 残留，`clampSentences` 按句数与字数硬裁剪，`parseJsonLoose` 用「先取代码围栏、再取首尾大括号、最后容错解析」三级降级。同时约束住输出通道：发言、共识提炼、总结各自走独立的 JSON schema 校验，校验不过就走降级路径而不是把原文透传到页面。**这件事让我对 Prompt 的定位变了：Prompt 负责「引导模型往对的方向走」，代码负责「保证走不到错的地方」。** 后者才是工程化的部分。

## 3. 我对「工程化 AI 开发」的理解

做完这个项目，我的理解可以压成一句话：**AI 让「写代码」这件事变便宜了，于是「定义什么是对的」变成了主要工作量。**

具体到三点体会：

**第一，AI 擅长的是「填空」，不擅长「划边界」。** 你告诉它「实现一个圆桌讨论引擎」，它会给你一版能跑的、看起来合理的实现；但「每次发言 1-2 句」「禁止机械式轮流发言」「共识要实时增量更新而不是结束时才生成」「多场讨论必须互相隔离」这些边界，它不会主动替你想。**划边界是人的工作**，而且必须写成可验收的形式（测试、断言、验收点），否则它只是一句愿望。

**第二，分层交付比一次生成更可控。** 一次让它生成整个项目，出问题时你面对的是一个巨大的黑盒；分层交付（契约 → 数据 → 引擎 → 接口 → 前端），每一层都有独立验证点，出错时能精确定位到某一层，而且模型在「小上下文 + 明确验收口径」下的输出质量明显更高。

**第三，工程化的痕迹应该留在仓库里，而不是留在对话里。** 契约文档、测试用例、分层提交历史、Prompt 记录，这些东西的价值不只是交付给评审看——它们是**下一次对话的输入**。我把 `docs/API.md` 当契约、把测试当验收口径，本质上是把「已经想清楚的部分」固化成 AI 可以反复读取的上下文，避免它在每一轮重新猜。这次 62 项测试全绿、前端 `tsc --noEmit` 与 `vite build` 双双通过、本地零配置可跑通完整讨论流程，靠的不是某一次特别成功的 Prompt，而是这套「先定契约 → 分层实现 → 每层验收」的流程本身。
