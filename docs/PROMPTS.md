# 核心 Prompt 记录

这份文档记录引导本项目从 0 到 1 落地的**原始 Prompt**，按开发范式分阶段整理。
每个阶段后附说明：当时想解决什么、遇到了什么挑战、如何引导 AI 修正。

## 阶段与范式对照

| # | 阶段范式 | 目标 | 主要产出 |
| --- | --- | --- | --- |
| P1 | **SDD**（规格驱动） | 数据建模与 API 契约生成 | `docs/PRD.md`、`docs/ER.md`、`docs/API.md` |
| P2 | **SDD → DDD** | 领域模型与数据层落地 | `domain/types.ts`、`schema.sql`、`repo.ts`、`seed.ts` |
| P3 | **DDD** | 设计上下文与前端组件拆解 | `.uicraft.md`、组件清单 |
| P4 | **TDD** | 核心逻辑的测试用例与业务实现 | `plan.test.ts`、`json.test.ts` → `plan.ts`、`json.ts` |
| P5 | **E2E** | 系统级端到端测试与质量闭环 | `tests/e2e/api.test.ts` |
| P6 | Prompt 工程（跨阶段） | 硬约束与输出容错 | `llm/`（types / prompts / json / mock / openai） |

> 使用的工具链：Claude Code（Vibe Coding 主体）+ DeepSeek V4 Pro（作为接入讨论引擎的真实模型）。

## P1 · [SDD 阶段] 数据建模与 API 契约生成

````text
你是这个项目的技术负责人。我们要做一个叫「AI Panel Studio」的本地 Web 应用：用户输入待讨论议题和参会专家
人数，系统调用大模型动态生成主持人 + 专家阵容，用户确认后进入演播厅，观看一场 AI 驱动、实时推进的圆桌讨论。

在写任何一行业务代码之前，先把契约定死。请只输出文档，不要生成代码。

交付三份 md：

1. docs/PRD.md —— 产品定位、目标用户、核心流程（发起 → 生成阵容 → 确认 → 开播 → 收尾）、
   每个流程的验收口径，以及明确的「不做清单」。

2. docs/ER.md —— 用 mermaid erDiagram 画出数据模型。至少要能承载：讨论、嘉宾、发言记录、
   共识/分歧条目、事件流、预置议题。每个实体标注主键、外键，以及「为什么需要这个字段」。

3. docs/API.md —— 完整的 REST 契约 + SSE 事件契约。要求：
   - 每个接口给出方法、路径、请求体、成功响应、错误码（400 / 404 / 409 / 500）；
   - 定义核心资源形状（Discussion / Panelist / TranscriptEntry / Insight）的 TypeScript 接口；
   - 画出讨论引擎的 mermaid sequenceDiagram；
   - 画出讨论状态机的 mermaid stateDiagram。

硬性约束，请写进文档并在后续所有代码里遵守：
- 大模型 API Key 只能在后端从环境变量读取，绝不能出现在任何前端代码、前端产物或 API 响应里；
- 数据库必须是 SQLite；
- 支持多场讨论并行，状态 / 事件流 / transcript / 共识分歧必须互相隔离；
- 实时推送用 SSE 或等价机制；
- 中文 UI。

先只做这一件事。完成后停下来等我确认。
````

**说明**：把「契约」当成第一阶段唯一的产出，是为了让后面每一层都有可对照的验收基准 —— 写数据层、引擎层、前端时我都不需要再向 AI 复述一遍产品，只需要让它「按 docs/API.md 实现」。
刻意加了一句「不要生成代码」：一旦让模型同时输出文档和实现，它就会用实现细节去迁就文档，契约里该有的边界情况反而被跳过。同时把「不做清单」列为必填项，避免模型顺手把通知、权限、多用户这些 MVP 之外的东西塞进来。

## P2 · [SDD → DDD 阶段] 领域模型与数据层落地

````text
现在按 docs/API.md 实现后端数据层，只做这一层。

范围：server/src/domain/types.ts、server/src/db/schema.sql、server/src/db/mappers.ts、
server/src/db/repo.ts、server/src/db/seed.ts。

要求：

1. domain/types.ts：把 API.md 里的资源形状落成 TS 类型，字段名与文档逐字一致。

2. schema.sql：6 张表（discussion / panelist / transcript_entry / insight / discussion_event /
   preset_topic）。注意：
   - 用 snake_case 存库、camelCase 出领域对象，映射统一放 mappers.ts；
   - discussion 的轮次字段命名为 round_no（round 是 SQL 关键字）；
   - transcript_entry 与 discussion_event 必须共享同一个单调递增的 seq，这是 SSE 断线续传的游标；
   - 外键全部 ON DELETE CASCADE。

3. repo.ts：所有 SQL 只能出现在这个文件里。必须做到：
   - appendTranscript 在一个事务里同时写 transcript_entry 和 discussion_event，保证两者 seq 一致；
   - listSummaries 用一次批量查询取 palette，禁止 N+1；
   - reconcileInsights 按归一化后的 statement 对账：已存在则合并支持者并把 emerging 升级为
     stable，不存在则插入。

4. seed.ts：至少 5 条预置议题（含议题、背景、标签、建议嘉宾阵容），以及 3 场已物化的样例讨论。
   样例数据必须走 repo 的正常写入路径，不许直接写 SQL 塞数据。

先给我 schema.sql + types.ts，我确认后再写 repo 和 seed。
````

**说明**：这里的关键是把「一致性要求」写成可检查的约束（同 seq、事务、禁 N+1），而不是交给模型自由发挥 —— AI 默认会写「先插 transcript 再插 event」这种两步写法，而这两步之间一旦出错，SSE 游标就会错位，前端表现为「断线重连后丢了几条发言」这种极难定位的问题。
要求 seed 走 repo 的正常写入路径，等于让 seed 阶段就把整条数据链路跑一遍：schema 写错会立刻暴露，而不是等到接口层才发现。

## P3 · [DDD 阶段] 设计上下文与前端组件拆解

````text
进入前端。先不要写页面，先做两件事：定设计方向，再拆组件。

第一步：在项目根写 .uicraft.md，包含四节 —— Users（谁在用、什么场景）、
Brand Personality（三个词的品牌个性 + 情绪目标 + 语气）、
Aesthetic Direction（主题、色彩主张、排版、反参考）、
Design Principles（4-5 条可检查的设计原则）。

设计方向已定，不要改成通用 SaaS 后台：
- 深色单主题（演播厅暗场），不做浅色切换；
- 主强调色用舞台琥珀金 #E7B24A，而不是默认的 SaaS 蓝；「ON AIR」用低饱和朱红；
- 每位嘉宾一个独立高辨识度色相，且这个颜色必须在状态灯、发言色块、共识/分歧标签三处保持一致
  —— 颜色即身份，用户靠颜色而不是读名字来追踪谁在说话；
- 标题用衬线体（编辑部质感），正文无衬线，时间戳等宽；
- 反参考：通用蓝色仪表盘、无差别卡片网格、毛玻璃、装饰性光晕、渐变文字。

第二步：在 .uicraft.md 的约束下拆组件。页面只有三个：
- 首页（讨论列表 + 发起入口 + 预置议题库）
- 发起页（填议题 → 生成阵容 → 逐位微调 → 确认）
- 演播厅（三栏：嘉宾席状态小窗 / 现场 Transcript / 实时共识与分歧 + 主持人总结）

硬性布局约束：整页不滚动。每个区域在自己的容器里独立滚动。超宽屏三栏并列、常规桌面收成两栏、
窄屏单栏 + 区域切换，但每个区域的滚动边界始终是它自己的容器。

先输出 .uicraft.md 和组件清单（每个组件一句话职责 + 它消费哪些契约字段）。我确认后再写代码。
````

**说明**：先定设计上下文再拆组件，是为了避免 AI 直接落到「卡片网格 + 蓝色主色」这个产品类别的中位数上 —— 没有明确的美学约束时，它一定会选最通用的那个。
把「颜色即身份」写成必须三处复用的约束，是因为它直接决定了组件接口的形状：transcript 组件和共识板组件都必须接收嘉宾色，而不能自己造色，否则同一个人的颜色在不同区域会对不上。
「整页不滚动」提前写进约束同样重要 —— 布局约束如果在实现之后才提，就要推翻整个页面结构。

## P4 · [TDD 阶段] 核心逻辑的测试用例编写与业务实现

````text
进入核心逻辑。这部分不允许先写实现 —— 先写测试，我确认测试用例合理之后再写实现。

先只输出测试文件：

1. server/tests/unit/plan.test.ts —— 发言顺序决策。要求覆盖：
   - 反驳优先于补充、补充优先于抢答、抢答优先于附和；
   - 同优先级按 urgency 降序；
   - 同一轮内同一位专家只出现一次；
   - 首轮必须让全部专家都有机会表态，不能有人整场沉默；
   - 无人主动发言时要有兜底（否则讨论会卡死）。

2. server/tests/unit/json.test.ts —— 模型输出容错。要求覆盖：
   - 包了 ```json 围栏要能解析出来；
   - JSON 前后有寒暄句要能解析出来；
   - 字段类型不对（该是数组给了字符串）要返回兜底值而不是抛错；
   - cleanUtterance 必须把「1-2 句」这条产品要求兜住：3 句要截成 2 句，超长句要截断。

测试写完后我会跑一遍，全部失败是预期的。然后再把 plan.ts / json.ts 的实现补上，让它们变绿。

注意：测试里要断言「为什么」而不是「是什么」，每个用例上面写一行注释说明它在防什么。
````

**说明**：TDD 阶段的价值不在「先写测试」这个动作，而在于让 AI 先把边界情况列全 —— 一旦让它先写实现，它只会覆盖 happy path，而「无人主动发言导致讨论卡死」「首轮有人整场沉默」这类边界，只有在写测试时才想得起来。
这一轮的实际产出也印证了这点：`plan.test.ts` 里「同轮去重」那条用例，后来真的抓出了实现里的重复发言缺陷。

## P5 · [E2E 阶段] 系统级端到端测试与质量闭环

````text
现在写系统级端到端测试：server/tests/e2e/api.test.ts。完全走 HTTP，用 supertest 打真实 Express
应用，不要 mock 引擎 —— 通过 vitest.config.ts 注入 LLM_MOCK=true 和 TURN_INTERVAL_MS=0，
跑的是与生产同一套编排代码，只是把模型换成离线确定性实现。

必须覆盖五组：

1. 健康检查与样例数据：/api/health 的响应里绝不能出现密钥（用正则断言响应体里没有
   api-key / sk- 字样）；预置议题 ≥ 5 条且每条都带嘉宾阵容。

2. 参数校验与状态机：议题过短 400；专家人数超出 2-6 拒绝；未生成阵容就 start 要 409；
   不存在的讨论 404；讨论开始后不允许再改阵容 409。

3. 主链路：创建 → 生成阵容 → 微调一位嘉宾 → 开始 → 等引擎自然跑完 → 校验：
   - transcript 首条是主持人开场、末条是主持人总结；
   - 每位嘉宾都至少发过言；
   - 每次发言 1-2 句（主持人收尾总结按设计是整段，要单独排除）；
   - 共识与分歧都在过程中被提炼出来了；
   - 总结是自然语言，不含 { 也不含 ``` 围栏；
   - transcript 里不出现「举手 / 抢答」这类内部事件。

4. 多讨论并行隔离：两场同时 start，跑完后两边的嘉宾 id 集合完全不相交，每场发言与共识都带正确的
   discussionId，总结各自包含自己的议题。

5. SSE：连接后首帧必须是 snapshot，随后能观察到 discussion.status / transcript.append /
   panelist.status / insight.upsert / summary.final 五类事件，且 seq 单调不减。

跑完把失败项列出来，先不要改代码，我们逐条判断是测试写错了还是实现有 bug。
````

**说明**：把「先不要改代码，逐条判断是测试写错了还是实现有 bug」写进 Prompt 是关键 —— 否则 AI 遇到红测的第一反应是去改断言让它变绿，而这恰恰会掩盖真实缺陷。
这一轮实际跑出 7 个失败：3 个是测试自己写错了（例如把无标点长文本的截断长度算错了一位），4 个是真实问题（e2e 用的内存库没有 seed 预置数据、句数断言没有排除主持人总结、离线引擎的共识池组合条件不满足、状态校验漏了 `ready` 态）。逐条分类而不是一把改绿，才让这些问题各自被正确归位。

## P6 · [跨阶段 · Prompt 工程] 硬约束与输出容错

````text
现在做 LLM 接入层：server/src/llm/。这一层的目标不是「把 prompt 写漂亮」，而是
「让模型的不确定性不破坏产品承诺」。

1. types.ts：定义 LlmEngine 接口，六个方法：generatePanel / hostCue / decideSpeakers /
   composeUtterance / synthesize / composeSummary。每个方法只接收它真正需要的上下文
   （而不是把整场讨论塞进去），接收的类型里不要出现任何数据库行结构。

2. prompts.ts：为每个方法写提示词。必须把下面这些写死进提示词：
   - 每次发言控制在 1-2 句，口语化，禁止空话与套话；
   - 禁止机械式轮流发言，专家要基于当前 transcript 自主决定发言顺序与姿态；
   - 只输出 JSON，不要任何解释文字；
   - 共识/分歧要基于已有发言，不许编造没出现过的观点；
   - 主持人总结用自然语言，禁止把 JSON 原文输出到页面上。

3. json.ts：写容错层。真实模型即使被要求「只输出 JSON」也可能包围栏、加寒暄、字段类型写错。
   extractJson 要能剥离噪声，所有 as* 取值函数解析失败时返回兜底值而不是抛异常
   —— 单次解析失败不能导致整场讨论崩掉。

4. mock.ts：写离线确定性引擎，用 mulberry32 做种子随机，内置 6 个立场原型与共识/分歧组合池。
   它必须能在不联网的情况下把一场讨论完整跑完。

5. openai.ts：OpenAI 兼容实现。要求：
   - 用 AbortController 做超时；
   - 错误信息只回显 HTTP 状态码与截断后的响应正文，绝不回显请求头或密钥。

每写完一个文件停下来给我看，不要一次性全写完。
````

**说明**：这一层的核心认识是「产品承诺不能只靠 prompt 兜住」。提示词里写「1-2 句」，但模型可能给 3 句，所以 `cleanUtterance()` 必须在落库前再切一次句 —— Prompt 是引导，代码才是保险。
要求 mock 引擎「能在不联网的情况下把一场讨论完整跑完」，是把可测试性反过来变成对架构的约束：它逼着我把「讨论怎么推进」和「模型怎么回答」彻底解耦，最后 `DiscussionRuntime` 完全不知道自己用的是真模型还是规则引擎，测试也因此不需要 mock 任何网络。

## P7 · [交付阶段] 文档、提交历史与工作流复盘

````text
收尾，三件事：

1. README.md：运行指南（含零配置离线演示）、环境变量表、技术选型说明（每个选型写「为什么」
   而不是「是什么」）、主要 API 列表、已完成能力清单、后续改进方向。
   要求每条改进方向都具体到「现在怎么做的 → 局限在哪 → 可以换成什么」，
   不要写「优化性能」这种空话。

2. docs/PROMPTS.md：把这次开发的核心 Prompt 按阶段整理出来，至少 5 段，每段明确标注对应的
   开发范式（SDD / DDD / TDD / E2E / Prompt 工程 / 交付），每段后面附 1-2 句说明：
   当时想解决什么、遇到了什么挑战、如何引导 AI 修正。
   说明要写真实发生的事，包括 AI 一开始做错的地方。

3. docs/WORKFLOW.md：1-1.5 页，写清楚：如何用 Claude Code 结合 DeepSeek V4 Pro 推进开发、
   遇到的 2-3 个典型问题及解决路径、对「工程化 AI 开发」的理解。

另外，把整个项目按层级做 git 提交，提交历史要能看出「契约 → 数据 → 界面 → 测试 → 业务逻辑」
的分层推进，不要把几十个文件塞进一个 commit。
````

**说明**：把「说明要写真实发生的事，包括 AI 一开始做错的地方」写进 Prompt，是因为复盘文档最容易退化成自我表扬。
实际的失败清单（无标点截断的边界算错、内存库没有 seed、句数断言没排除总结、共识池条件不满足、状态校验漏了 `ready` 态）比任何成功案例都更能说明「工程化 AI 开发」到底在防什么。
要求提交历史体现分层，则是把「工程化拆解」这个考核点落成一个可被客观检查的痕迹。
